# Digital Human Video

Turn the user's topic, script, and production preferences into an avatar video. Style, framing, duration, language, voice, tone, movement, background, captions, and output format are per-run choices—not fixed presets. Honor explicit preferences; ask only when a missing choice materially changes the result. Otherwise use the least surprising choice for the context and say what you assumed: for slide overlays, prefer transparency if supported; for a self-contained scene, use a restrained topic-appropriate background. Never assume a solid-color backdrop is transparency. Choose the route the user requested; never switch between Muse and local inference silently. For Muse runs, generate character art, silent video, and spoken audio as separate assets, then combine them locally with FFmpeg before QA.

## Resolve the run requirements

1. **Intake once.** Capture the topic, exact narration, audience/use, visual style or reference and mood/palette, framing/aspect ratio, target duration and ending behavior, language/accent/voice/tone/emotion/pace, facial and body motion/gestures/camera, background policy, captions/on-screen text, target resolution/frame rate, output format, and destination app when provided. These are options, not a mandatory questionnaire: ask only for missing information that materially affects the result. Preserve supplied copy verbatim; do not invent or rewrite narration. The 20-Unicode-grapheme limit (punctuation included) applies only to this project's current local FastAPI route, not to the Muse/browser workflow. Validate it before local submission; if exceeded, ask whether to split the text into multiple jobs or choose another route. Do not truncate, rewrite, or switch routes silently. Check a provider's actual limits when needed; if the requested timing cannot fit the text naturally, ask before rewriting or speeding it up.
2. **Choose or make one avatar.** Reuse an approved existing avatar when the user wants continuity and it fits the request; an image in Muse chat may be reused there, but a local or Codex image is not automatically visible to Muse. Otherwise use ImageGen once to create an original character suited to the topic, requested art style, intended crop, and animation. Do not force cartoon, full-body, a particular gender, or a fixed aspect ratio. Keep identity stable across a requested series, with a clear unobstructed face and limbs suited to the requested movement. Include or omit scenery, shadows, text, logos, and topic motifs according to the request; do not make unrequested variants.
3. **Verify and stage the image.** Check the requested style, topic fit, crop, identity, and visible face/body details. When transparent output is requested, verify the PNG has actual alpha pixels—not a checkerboard or an image depicting transparency. If transparency is unavailable, ask before background removal or accepting an opaque substitute. Save the selected image to a unique ignored path such as `outputs/avatars/<topic-slug>/avatar.png`; do not overwrite an existing avatar.
4. **Generate the silent video in Muse.** Use `mcp__cua_repl.js` on the user's explicitly selected Chrome tab. Confirm it is the intended Muse chat and leave unrelated tabs untouched. Attach only the selected avatar. Request the specified style, framing, duration, background, and motion; describe facial expression, gaze, mouth movement, blink rate, gestures, and camera only as needed to realize that request. For speech, animate as if delivering the exact line while keeping mouth movement natural and proportionate. Avoid unrequested redesign, erratic gaze, excessive expression, or malformed hands. Request genuine alpha only when the user wants a transparent overlay; if Muse's alpha capability is unclear, ask before spending credits to test it. If exact duration or an output option is unsupported, use a documented nearest option only if it preserves intent; otherwise ask. Do not silently substitute a solid/chroma-key background for alpha or vice versa.
5. **Generate the voice as a separate asset.** In a distinct audio-generation task, request the exact line in the requested language, accent, voice qualities, tone, emotion, and pace. If these are unspecified, use the narration's language, a clear natural delivery appropriate to the topic, a neutral accent, and no gender assumption. Request a clean audio-only WAV, or MP3 if WAV is unavailable, unless another format was requested; omit music, effects, intro, and outro unless asked. Do not rely on audio embedded in the video. Ask before switching provider or route if Muse cannot provide separate audio.
6. **Wait for both Muse tasks.** Track the single video job and the single audio job using fresh UI state; do not refresh, resend, or duplicate either generation. Check after about 10–15 seconds, then every 20–30 seconds while working; give a concise update if the wait exceeds a minute. A disconnected/offline label alone is not a blocker if the user explicitly said to use the composer. Stop and ask if Muse requires a purchase, upgrade, legal acceptance, new permission, or another unapproved action.
7. **Collect and inspect the separate assets.** Download the video and audio through Muse's visible controls to a temporary review folder; verify they are non-empty. Use `ffprobe` to check duration, dimensions, codecs, audio stream, and alpha when requested. Inspect several frames against the intended background (checkerboard for alpha) and review style, identity, framing, facial/body motion, speech delivery, and artifacts against the user's preferences. Listen to the voice or verify it with a reliable transcript. Do not claim lip-sync, timing, or transparency unless checked. If Muse omitted an asset or returned the wrong background, keep the source and ask before another paid generation or corrective processing.
8. **Combine the requested audio and video locally with FFmpeg.** Preserve the full spoken-audio duration. Apply the requested ending behavior (trim, hold, loop, or tail) when durations differ; do not force `-shortest` if it would contradict that choice. The ProRes 4444 examples below apply only when transparent delivery was requested. Give the picture about 0.1 seconds of extra tail so `-shortest` cannot clip the final audio packet. Convert genuine-alpha source to a ProRes 4444 MOV master without flattening alpha (skip this conversion if Muse already returned ProRes 4444):

   ```bash
   ffmpeg -i muse-alpha-video.mov -an -vf format=yuva444p10le -c:v prores_ks -profile:v 4444 -alpha_bits 16 avatar-alpha.mov
   ```

   Verify that `avatar-alpha.mov` still contains transparency. When it is at least as long as the voice track, mux without re-encoding that video stream, for example:

   ```bash
   ffmpeg -i avatar-alpha.mov -i narration.wav \
     -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -b:a 192k \
     -shortest slide-ready-alpha.mov
   ```

   For a non-transparent deliverable, encode/mux in the requested container and codecs. If no compatible format was specified, H.264/AAC MP4 is a practical general-purpose fallback. Test playback in the actual destination app/device when possible. Do not label an ordinary MP4 transparent. If the destination cannot play the requested alpha format, ask which compatible background/export they prefer. [FFmpeg's ProRes documentation](https://ffmpeg.org/ffmpeg-codecs.html#ProRes) describes its 4444 profile and alpha support. PowerPoint lists QuickTime `.mov` as a supported container but recommends H.264/AAC MP4, so test alpha playback in the user's actual slide app and platform before relying on it ([supported formats](https://support.microsoft.com/en-us/powerpoint/video-and-audio-file-formats-supported-in-powerpoint)).
9. **Verify and save the final asset.** Check the combined file has the expected streams, duration, background/alpha behavior, and format; inspect and play it in the target app when available. Save the avatar, separate source audio/video, and final output in a unique ignored folder such as `outputs/muse-<date>-<topic-slug>/`. Keep generated/private media out of commits and label Muse work as external/browser-generated.

### Reusable Muse prompt shape

Use separate concise prompts and keep the actual topic and narration exact:

**Silent video:** Use the attached image as the character reference. Topic: **[topic]**. Requested style, visual mood/palette, framing/aspect ratio, resolution, and frame rate: **[specify]**. Target duration and ending behavior: **[specify or provider-supported default]**. Background: **[transparent / solid color / scene / other requested treatment]**. Animate as if saying “**[verbatim line]**” but generate no audio. Apply the requested facial/body motion, expression, gaze, gesture, and camera movement: **[specify]**. Captions/on-screen text: **[exact text or none]**. Preserve identity and avoid unrequested redesign or extra people. Return one silent video file in the requested format.

**Separate audio:** Say exactly in **[language/accent]**: “**[verbatim line]**”, using **[requested voice, tone, emotion, and pace; otherwise a clear natural delivery suited to context]**. Return one clean audio-only **[requested format; otherwise WAV or MP3]**, without music, sound effects, intro, or outro unless requested.

For a series, reuse the selected avatar and its preprocessing/cache when the user wants identity continuity; change it only when requested or necessary for a genuinely different character/style. Do not regenerate just because narration changes.

## Browser and data boundaries

The Muse route sends the selected image and requested text to an external provider. Only a user request for this ImageGen→Muse workflow authorizes sending the image generated/selected for this run and its narration—not other portraits, voice recordings, credentials, project files, or conversation history. If uploading a local image, identify that exact file and destination. If Chrome's file chooser fails, do not weaken extension permissions or silently substitute an in-chat avatar. Tell the user: “To enable file upload, open `chrome://extensions`, click **Details** under the ChatGPT browser extension, and enable **Allow access to file URLs**.” See the [Chrome file-upload instructions](https://developers.openai.com/codex/app/chrome-extension#upload-files). Never change the permission yourself. Do not accept legal terms, buy credits, or upgrade plans without action-time approval; if the visible cost is not covered by the user's request or included balance, stop and ask.

## Local pipeline (only when requested)

Before setup, read the project README, `.env.example`, and third-party notices. Confirm Apple Silicon/macOS before recommending MLX/MPS, and use the documented Qwen3-TTS/MLX path for local Chinese speech. Run `scripts/demo_fake.sh` before installing model weights; for a real render, follow the pinned setup and checksum scripts, keep MuseTalk and LivePortrait in separate environments, and run only one render at a time on a 24GB Mac. Apply the local API's documented constraints (including its current Chinese grapheme limit) only when this local route is selected; do not present them as universal provider limits. Reuse avatar preprocessing for a stable identity. Choose the cached LivePortrait loop when the user wants facial/head movement without waveform-timed lips, noting the loop is not speech-driven; choose MuseTalk only for requested approximate audio-driven lip motion and inspect for deformation. Keep the unauthenticated FastAPI service and MuseTalk sidecar on `127.0.0.1`. Until the detector licensing issue is resolved, use LivePortrait only with `--noncommercial-research` for genuinely non-commercial work. Report whether results were verified on real hardware or only through the fake/simulated path. If the user reports local video inference freezes the computer, stop and do not retry unless explicitly reauthorized.

## Release and commercial checks

Before packaging, inspect third-party notices and model terms. LivePortrait's license flags InsightFace detection models as non-commercial research only; commercial users must replace them with a commercially licensed detector or obtain permission. Never describe that setup as commercially cleared until the detector issue is resolved. For Muse, separately review provider terms for uploaded images/text, generated audio/video, commercial use, retention, and export. `BUYER-LICENSE.txt` grants only the purchasing customer use and private modification; it prohibits sharing, resale, and redistribution and must be included with every paid package. It does not grant rights to models, code, inputs, identities, voices, or outputs.
